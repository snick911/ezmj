# EZMJ 網頁版客戶端評估

2026-11-02 的討論紀錄。**已開工**，專案是 [`ezmj_web`](https://github.com/snick911/ezmj_web)。技術改用 Java 加 TeaVM，不是當初建議的 TypeScript。建置、程式結構與和 Swing 版的差異以它的 README 為準，這份留下當初的評估與決定。

## 結論

| 項目 | 內容 | 狀態 |
|---|---|---|
| 專案 | 獨立專案 `ezmj_web`，不放進 `ezmj` 或 `ezmjService` | 已決定 |
| 範圍 | 先做連線對戰；跟電腦打用一人房間，由服務器補三家電腦 | 已決定 |
| 麻將邏輯 | 不重寫，全部由服務器跑 | 已決定 |
| 技術 | 用 Java 寫，TeaVM 編成 JavaScript。牌桌畫在 Canvas，對話框與選單用 HTML/CSS | 已決定 |
| 部署 | 靜態網站（Render 靜態網站或 GitHub Pages），不由服務器提供網頁 | 已決定 |
| 工作量 | 開工前估一個人約 2–3 週，手機版另外多約 1 週 | 粗估 |

## 麻將邏輯

連線版的胡牌判定、計台、行牌流程與電腦玩家都在服務器上跑，服務器直接用 `ezmj` 的引擎。能不能吃碰槓、打哪張會聽，也是服務器算好送來的。

網頁只需要顯示用的小邏輯，`ezmj` 原始碼有的就直接編譯，不另外寫：

- 把牌的代碼轉成牌名，例如 `1w` 是一萬
- 把服務器座位轉成畫面座位，自己固定在下方
- 吃牌有多種組合時，讓玩家選牌

### 單機模式

| 做法 | 評估 |
|---|---|
| 一人房間，由服務器補電腦 | 採用的做法，幾乎不用多做 |
| 手動把規則與電腦玩家移植到 JS | 不建議。約 4,900 行，之後規則要維護兩份 |
| 用 TeaVM 把 Java 引擎編成 JS | 真的需要離線時再試，規則不會有兩份。網頁已經用 TeaVM，但沒有用到 `TableFlow`，所以牌局流程還沒在瀏覽器跑過。`TableFlow` 沒有用到執行緒，但存檔的檔案讀寫要另外處理。還沒驗證 |

一人房間的限制：

- 服務器要在線上，免費主機睡著後，第一次連線可能要等約一分鐘
- 不能設定不限時，最長每步 300 秒
- 沒有電腦代打
- 不能存檔，每次部署服務器都會中斷進行中的牌局
- 網頁版沒有本機的統計與成就

## 畫面

| 部分 | 能多像 | 原因 |
|---|---|---|
| 牌桌、牌面、花牌圖案 | 幾乎一樣 | 現在就是用 Java2D 自己畫的，座標、路徑和顏色可以搬到 Canvas |
| 動畫 | 幾乎一樣 | 飛牌與大字的時間都是程式裡的常數，可以照用 |
| 牌面的字 | 嵌入同一套字型才會一樣 | 標楷體不能隨便放上網，改用可授權的楷書字型時字形會略有差異 |
| 按鈕、對話框、選單 | 風格相同，細節略有差異 | 改用 HTML/CSS，顏色和尺寸可以照 `Theme` |
| 視窗大小 | 要調整 | 從固定解析度選項改成跟著瀏覽器縮放 |

文字邊緣的鋸齒和粗細會有些微不同，因為瀏覽器和 Java 的文字繪製方式不一樣。

手機是例外：版面是照桌機大視窗設計的，手機直向放不下，橫向也會很小，要做手機版就得另外調整版面。

以上是開工前讀程式碼後的判斷。實際的差異見 `ezmj_web` README 的「和 Swing 版的差異」。

## 專案與部署

### 為什麼不放進 `ezmj`

當初的理由之一是沒有共用的程式碼，這點已不成立：網頁直接編譯 `ezmj` 的 `model`、`online`、`rules` 原始碼，也用到 `engine` 的 `RoundView`、`Claim` 等。但這和 `ezmjService` 一樣，只是建置時讀隔壁的資料夾，不用放在同一個 repo。其他理由還成立：

- 發布節奏不同：兩邊各自有版號與 `CHANGELOG.md`，網頁打包後上傳到靜態網站，不用等 Swing 發布
- 網頁的 `pom.xml`、TeaVM 與靜態檔和 `ezmj` 的 `build.ps1`、Eclipse 設定無關，`ezmjService` 建置時抓 `ezmj` 原始碼也用不到它們
- `ezmjService` 已經是獨立專案，各自有版號與修改紀錄，照同樣的方式做就好

放在一起的好處是畫面修改可以用一個 commit 同時改兩邊，但還是要改兩次。

### 為什麼不放進 `ezmjService`

放在同一個 repo 的好處是改協定時可以一起改，但有兩個麻煩：

- 現在 push 到 `main` 就會部署服務器，只改網頁時要記得加 `[skip render]` 或另外設定路徑過濾，忘了就會中斷所有人的牌局
- 服務器的版號和 `CHANGELOG.md` 是照協定相容性訂的，網頁的修改放進去會看不出哪些改動影響服務器

### 為什麼不由服務器提供網頁

- 每次部署都會結束進行中的牌局，token 也會失效。網頁放在服務器裡，修一個錯字也要重新部署
- 免費主機閒置後會睡著，玩家可能要對著空白頁等約一分鐘。靜態網站可以馬上打開，並顯示「正在喚醒服務器」
- `WebSocket.java` 是手寫的 HTTP，只處理 `/healthz` 和 `/ws`。要提供網頁就得自己處理檔案路徑安全、檔案類型和快取

服務器沒有檢查 Origin，所以網頁不必和服務器同源。

### 連線方式

網頁直接連現有的 `wss://ezmj-server.onrender.com/ws`，服務器不用改。測試時要換成本機服務器，不要碰到線上的。

## 風險與要處理的事

1. **長期維護**：最大的成本。之後 Swing 和網頁是兩份畫面，改畫面或動畫都要做兩次。
2. **字型**：牌面的字用系統楷書（如 `DFKai-SB`），各裝置不一定有。沒有時用嵌入的霞鶩文楷 TC 子集，授權是 OFL。
3. **語音**：現在靠 Windows 語音合成，瀏覽器不能用。先用 Web Speech API，但聲音會因裝置而異，沒有中文語音的裝置不出聲。
4. **音效與音樂**：把合成程式移植過去，公式與樂譜和 Swing 版一樣。瀏覽器要等使用者點過畫面才能出聲。
5. **背景分頁**：服務器 60 秒沒收到訊息就斷線，而瀏覽器可能放慢背景分頁的計時器，手機切到背景也可能斷線。收到訊息時會順便檢查該不該送 ping，真的斷了就靠重連機制接回牌局。真正的背景分頁與手機還沒驗證。
6. **資安**：token 要存在瀏覽器裡，玩家名字不能用 `innerHTML` 顯示，否則 token 可能被偷。
7. **版本不合**：分開部署後，瀏覽器可能還留著舊版網頁。服務器拒絕登入時要提示玩家重新整理。
8. **協定版本**：網頁的 `PROTOCOL` 來自 `ezmj` 的 `OnlineClient.PROTOCOL`，重新編譯就跟上，但新訊息的處理要另外改。協定改了要連網頁一起看，這點已寫進 `ezmjService` 的 README。
9. **畫面同步**：`ezmj_web` 的 README 記下對應哪一版 Swing 的畫面，目前是 0.6.0，之後才查得出哪些修改還沒跟上。

## 實測結果

開工前在瀏覽器裡用 JavaScript 直接連本機的 `ezmj-server-0.2.0.jar`，沒有改服務器，也沒有碰線上的 Render。

| 項目 | 結果 |
|---|---|
| 登入、開房、開局 | 成功 |
| 收局面與事件 | 成功，約 18 秒內收到 `state` 與 `event` 各 99 則 |
| 打牌、過牌 | 成功，沒有收到錯誤 |
| 關掉連線後用 token 重連 | 成功，補回局面後繼續打 |
| 跨來源連線 | 從 `localhost` 連 `127.0.0.1` 沒有被擋，但只送了 `ping` 和 `honorRoll`，沒有打牌 |
| `honorRoll` | 回 `notLoggedIn`。本機的 0.2.0 jar 比原始碼舊，這個訊息還在「未發布」，不是瀏覽器的問題 |

開工後用 `ezmj_web` 的網頁對同一個本機 jar 驗證過：

- 打完一整場，破產結束與四圈打完都有
- 斷線重連
- 接回牌局

還沒有驗證：

- `wss://` 與 Render 上的連線
- 真正的背景分頁
- 手機
